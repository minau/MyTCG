# MyTCG V2

## Périmètre livré

Univers publics/privés, adhésions, invitation privée consultable et régénérable, sélection contextuelle, Studio, illustrations, catalogue, collection et progression, boosters quotidiens avec historique et idempotence, decks incomplets ou valides et sélection du deck principal. La navigation Combat affiche une attente. Aucun combat, paiement, monnaie, échange, marché ou service IA n’est ajouté.

Le web reste Blazor WebAssembly et le mobile reste MAUI natif. Les vues partagent les contrats typés et le transport authentifié `AuthClient`. Le web affiche un tiroir droit utilisable au clavier (focus, boucle Tab, Échap, clic extérieur), des grilles adaptatives et une révélation progressive avec raccourci pour tout révéler. Le mobile dispose d’un tiroir, de vues tactiles et de révélations commandées par le joueur.

## Architecture

- **Domain** : `Tcg`, `TcgMembership`, `TcgInvitation`, `Card`, `UserCard`, `BoosterOpening`, `BoosterOpeningCard`, `Deck`, `DeckCard`, énumérations de visibilité, rôle, type et rareté.
- **Contracts** : requêtes et réponses REST typées ; les valeurs d’énumérations JSON restent des entiers (Public=0, Private=1 ; Character=0, Action=1 ; Common=0 jusqu’à Legendary=4).
- **Application** : `ITcgService`, `IMediaStorage`, erreurs métier structurées.
- **Infrastructure** : implémentations EF/Npgsql, `BoosterOpeningService` dédié, configuration des contraintes, stockage local abstrait, protection des invitations. Cette localisation suit le service de compte de V1.
- **API** : endpoints minimaux séparés dans `TcgEndpoints`, authentification V1 conservée, autorisation applicative par membre/créateur ; CORS étendu à PATCH/DELETE.
- **Client** : appels JSON, commandes, upload binaire et lecture de médias privés avec le jeton en en-tête. Aucun jeton n’est ajouté aux URL des images.
- **Web** : espace TCG, éditeur, composant de carte partagé entre Studio, collection, boosters et decks.
- **Mobile** : `TcgPage`, `NativeCardView`, point d’entrée depuis le compte existant.

Les rôles sont extensibles, mais seul le créateur obtient et utilise le rôle administrateur. Il n’existe aucun endpoint de promotion. Toutes les ressources imbriquées sont filtrées par TCG et propriétaire. Les clés étrangères composées interdisent d’associer une carte d’un univers à la collection, au booster ou au deck d’un autre univers.

Le changement de TCG efface les données affichées avant le chargement suivant. Une génération de chargement et la comparaison du TCG empêchent l’application d’une ancienne réponse. Les mutations désactivent le sélecteur pendant leur exécution. La sélection active n’est pas conservée entre sessions : c’est une option UX, pas une autorisation.

## Migration

`20261024181820_MultiTcgV2` ajoute les dix tables métier, leurs index, clés et contraintes. La migration et le snapshot EF sont générés. `InitialIdentity` et les tables V1 sont conservés.

Contraintes notables : adhésion unique `(TcgId, UserId)`, numéro de carte unique par univers, possession unique par joueur/carte/univers, idempotence unique par joueur/univers, une invitation non révoquée par univers, un deck principal par joueur/univers. Les quantités positives et le coût 1–12 ont également des contraintes SQL.

La suppression physique des cartes n’est pas exposée. L’archivage conserve possessions et decks. Les identifiants stables et les horodatages préparent une évolution vers le versionnement, sans l’implémenter. L’historique conserve l’ordre et les identifiants des cartes ; leurs détails sont ceux du catalogue courant, pas un instantané versionné.

## Boosters et probabilités

Configuration initiale dans `src/MyTCG.Api/appsettings.json` :

```json
"Boosters": {
  "DailyLimit": 3,
  "FifthMultipliers": [1, 2, 4, 8, 16]
}
```

Les quatre premières positions ont `P(carte i) = DropWeight(i) / somme(DropWeight)`, sur les cartes actives de cet univers dont le poids est positif. Les doublons sont autorisés, sans retrait après tirage.

La cinquième position multiplie le poids par 1 (Common), 2 (Uncommon), 4 (Rare), 8 (Epic) ou 16 (Legendary), puis renormalise sur les seules cartes disponibles. Exemple avec une carte de chaque rareté, toutes de poids 100 : positions 1–4, 20 % chacune ; position 5, respectivement 3,23 %, 6,45 %, 12,90 %, 25,81 %, 51,61 %. La probabilité Rare ou mieux passe de 60 % à 90,32 % dans cet exemple.

Une rareté absente n’a aucune masse réservée ; les cartes présentes sont renormalisées. Si toutes les cartes sont de même rareté, la distribution ne peut pas améliorer cette rareté. Un catalogue sans carte éligible refuse l’ouverture sans consommation. Les multiplicateurs doivent être finis, strictement positifs et croissants. Le poids d’une carte est limité à 10^12 pour garder des calculs bornés.

La date et le prochain renouvellement sont calculés par le serveur en UTC ; minuit UTC délimite le quota. Les ouvertures persistées font foi : aucun compteur parallèle à synchroniser. Une transaction PostgreSQL verrouille la ligne d’adhésion du joueur dans cet univers (`FOR UPDATE`) avant le contrôle du quota, l’idempotence, le tirage et l’écriture des récompenses. Ce verrou couvre les réplicas API. Une même clé retourne l’ouverture initiale, y compris si le quota est ensuite épuisé. La date est capturée une fois pour le contrôle et l’écriture, évitant un décalage à minuit.

Le hasard utilise `RandomNumberGenerator`. L’animation ne fait aucun tirage et commence après la validation de la transaction. Le client conserve sa clé en cas d’échec pour permettre une nouvelle tentative sans nouvelle attribution.

## Illustrations et persistance

`IMediaStorage` permet de remplacer le disque local par du stockage objet. JPEG, PNG et WebP fixes sont acceptés, jusqu’à 5 Mo, 4096 pixels par dimension et 16 millions de pixels. SkiaSharp décode le contenu, vérifie son format réel, refuse un décodage incomplet et réencode en PNG sous un nom UUID. Aucun nom client ni binaire n’est conservé en base. Les animations et SVG sont refusés.

Les uploads exigent l’administration du TCG ; les lectures exigent l’adhésion, y compris dans les univers privés. Les images privées sont chargées via le client authentifié. Le stockage local est Linux dans Docker avec les assets natifs SkiaSharp sans dépendances supplémentaires ; aucun service d’infrastructure n’est ajouté. Les couvertures de TCG utilisent une URL HTTPS facultative.

Les codes d’invitation contiennent 192 bits aléatoires. La recherche utilise SHA-256 ; une copie chiffrée avec ASP.NET Data Protection permet au créateur de consulter son code. La régénération révoque l’ancien code. Les clés de protection doivent donc être conservées et partagées entre les réplicas d’une même installation. Le volume de clés contient des secrets : le sauvegarder avec les médias et la base et limiter son accès.

Volumes Compose ajoutés : `media_data:/app/media`, `protection_keys:/app/keys`. `postgres_data` reste inchangé. Variables : `Media__Root`, `DataProtection__KeyPath`, `Boosters__DailyLimit`, `Boosters__FifthMultipliers__0` à `__4`. Les fichiers applicatifs et dossiers inscriptibles appartiennent à l’utilisateur non privilégié `app`. Médias, clés et fichiers de travail sont exclus du contexte Docker et de Git.

## API

Toutes les routes suivantes nécessitent une session Bearer V1. L’identité du joueur vient de `sub`, jamais du corps de requête. Préfixe `/api/tcgs` :

| Méthode | Route | Accès / résultat |
|---|---|---|
| POST | `/` | Créer un univers et son adhésion administrateur |
| GET | `/mine` | Mes univers |
| GET | `/public?search=...` | Catalogue public, recherche par nom, jusqu’à 100 résultats |
| GET | `/{tcgId}` | Détail réservé aux membres |
| POST | `/{tcgId}/join` | Rejoindre un univers public |
| POST | `/join-by-code` | Rejoindre via `{ "code": "..." }` |
| GET | `/{tcgId}/invitation` | Code privé, créateur seulement |
| POST | `/{tcgId}/invitation/regenerate` | Révoquer et remplacer le code |
| GET | `/{tcgId}/cards` | Catalogue, membres |
| POST | `/{tcgId}/cards` | Créer une carte, créateur |
| PUT | `/{tcgId}/cards/{cardId}` | Modifier une carte, créateur |
| PATCH | `/{tcgId}/cards/{cardId}/status` | `{ "isActive": false }`, créateur |
| POST | `/{tcgId}/media` | Corps binaire et Content-Type réel, créateur ; retourne `{ "url": "..." }` |
| GET | `/{tcgId}/media/{name}` | Lecture authentifiée du média, membre |
| GET | `/{tcgId}/collection` | Catalogue avec quantités du joueur courant ; quantité 0 pour les cartes non découvertes |
| GET | `/{tcgId}/collection/progress` | Distinctes, exemplaires, taille du catalogue |
| GET | `/{tcgId}/boosters/status` | Restants, limite, prochaine remise à zéro UTC |
| POST | `/{tcgId}/boosters/open` | `{ "idempotencyKey": "clé-unique-8-à-128-caractères" }` |
| GET | `/{tcgId}/boosters/history` | 100 dernières ouvertures du joueur, cartes ordonnées |
| GET / POST | `/{tcgId}/decks` | Lister / créer un deck |
| GET / PUT / DELETE | `/{tcgId}/decks/{deckId}` | Lire / enregistrer / supprimer son deck |
| PUT | `/{tcgId}/decks/{deckId}/primary` | Sélectionner son deck principal |

Un deck se transmet comme `{ "name": "Mon deck", "cards": [{ "cardId": "UUID", "quantity": 2 }] }`. Zéro à 16 cartes est accepté ; exactement 16 donne `isValid=true`. Les copies ne sont pas consommées et sont réutilisables dans d’autres decks. Un deck principal peut être incomplet, mais ne devient pas pour autant valide pour le futur combat. La récupération typée du deck et du catalogue fournit les informations au futur moteur sans ajouter de logique de combat.

Erreurs JSON `{ "code": "...", "errors": ["..."] }`. Statuts : 400 pour validation, 401 pour session, 403 pour adhésion/administration, 404 pour ressource absente/non possédée, 409 pour conflit métier (quota, catalogue vide, doublon d’adhésion/numéro détecté). Une course sur une contrainte d’unicité SQL utilise la réponse 400 `duplicate` existante.

## Lancement local avec Docker

Prérequis : Docker et Compose v2 récent (le fichier de développement utilise `!override`). Depuis le dépôt :

```bash
# Seulement si .env n’existe pas ; ne remplace jamais un fichier existant.
python3 scripts/init-env.py

docker compose --env-file .env -f deploy/docker-compose.yml -f deploy/docker-compose.dev.yml up --build -d
```

Ouvrir `http://localhost:8088`. API : `http://localhost:5080`, santé : `/health`, documentation OpenAPI interactive en développement : `/docs`. Le job `migrate` termine les migrations avant le démarrage de l’API. Ne pas lancer de migrations concurrentes manuellement dans chaque réplica et ne pas utiliser `down -v` si les données doivent être conservées.

En production OVH : renseigner les domaines et l’adresse ACME dans `.env`, DNS vers le serveur, ports 80/443 ouverts, puis :

```bash
docker compose --env-file .env -f deploy/docker-compose.yml up --build -d
```

Les secrets de V1 restent nécessaires (`POSTGRES_PASSWORD`, `JWT_KEY`), ainsi que les sauvegardes PostgreSQL/médias/clés. Aucun déploiement OVH n’est effectué par ce travail.

Pour une construction derrière un proxy TLS, les Dockerfiles acceptent un secret BuildKit optionnel, sans embarquer le certificat dans l’image :

```bash
docker build --secret id=build_ca,src=/chemin/ca-bundle.pem -f deploy/Dockerfile.api -t mytcg-api:local .
```

## Vérifications

```bash
dotnet restore MyTCG.Server.slnf --locked-mode
dotnet build MyTCG.Server.slnf --no-restore
dotnet test tests/MyTCG.UnitTests --no-build
dotnet test tests/MyTCG.IntegrationTests --no-build
```

Les tests d’intégration démarrent PostgreSQL 16 via Testcontainers. Une base de test dédiée peut être fournie par `MYTCG_TEST_DATABASE` ; ne pas utiliser la base de production. Les tests vérifient notamment : invitations révoquées, droits administrateur, cohérence inter-TCG, cinq cartes et doublons, cartes actives, quota concurrent, idempotence concurrente, frontière UTC, rollback après écriture SQL, absence de consommation sur catalogue vide, images valides/falsifiées et accès privé, decks de 16 cartes, copies partagées entre decks, propriété et unicité du principal. Les tests unitaires vérifient des intervalles de tirage déterministes, les multiplicateurs de cinquième carte, les raretés absentes et les validations des cartes.

Test navigateur, avec Playwright et Chromium installés :

```bash
PLAYWRIGHT_MODULE=/chemin/node_modules/playwright-core WEB_URL=http://localhost:5180 node scripts/smoke-v2.cjs
```

Le script couvre inscription/connexion, création TCG, Studio, prévisualisation, booster, collection, deck et principal, attente Combat, tiroir/Échap, changement de TCG et rendu 390 px. `smoke-web.cjs` conserve les contrôles de session V1 avec l’écran d’accueil V2.

## Limites de validation et évolutions

Les builds de paquets Android/iOS et les essais sur appareils physiques ne sont pas exécutés dans cet environnement Linux ; iOS exige un Mac/Xcode et Android son SDK/workload. Le code MAUI commun est vérifié par compilation contre ses bibliothèques. Les animations tactiles et l’accessibilité avec lecteurs d’écran restent à vérifier sur appareils.

Le catalogue public et l’historique renvoient les 100 premiers résultats ; une pagination sera utile à grande échelle. Le catalogue de cartes n’a pas de limite de 100 cartes. Le stockage objet, le versionnement et les invitations individuelles sont préparés par les abstractions et références stables, mais non implémentés. Le web réduit les animations via `prefers-reduced-motion`. La révélation est commandée par le joueur, et peut être passée entièrement.
